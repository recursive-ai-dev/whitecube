NETWORK SETUP, WHILE BOOTED INTO THE NVME

The included controller is your custom userspace connection controller over the
existing Linux network stack. It is scoped to USB 2001:3329, MAC
88:76:b9:f2:9d:29 and driver rtw88_8822cu. The audited target has the complete
driver dependency set and firmware. The new service is installed DISABLED,
pending saved-profile import or entry of your Wi-Fi credentials.

  cube-net check
  sudo cube-net import-nm

If there is no supported saved WPA2 profile, enter one locally instead:

  sudo cube-net setup

Then activate the scoped controller:

  sudo systemctl daemon-reload
  sudo systemctl enable --now whitecube-network.service
  cube-net status
  sudo cube-net reconnect   # new budget: at most three association attempts

The browser Network drawer shows association/signal/reconnect/error information
and saved profile names. Add, scan, connect and remove actions open the terminal
for authentication. Wi-Fi passwords never go in browser request arguments.
CLI equivalents: sudo cube-net manage, add, scan, connect PROFILE_ID or
remove PROFILE_ID. Existing profiles are retained when adding another. If an
older version of this controller is already enabled, reload systemd and restart
whitecube-network.service after upgrading to enable its public status publisher.

The controller refuses another manager or WPA controller that owns the dongle.
It never stops other controllers, restores modules or unmasks services. Its
credentials stay in a root-only local file. WPA2 personal + IPv4 DHCP are provided;
enterprise Wi-Fi, WPA3-only profiles and DHCPv6 are outside this implementation.
Carrier status is hardware link status, not proof of Internet access. Details
and rollback for networking are in network/README.txt.

FOUR DEBIAN CONTAINERS, 8 GiB DISK EACH

After booting the NVMe and establishing Internet access, provision all four:

  sudo cube-lab provision --install-tools

This is a separate step from installing the desktop files. It creates four real
debootstrapped Debian 13 trixie filesystems with fixed 8 GiB ext4 images (32 GiB
total capacity), installs each lab's tools, and leaves them ready for interactive
use. The current restricted session has prepared the setup but has NOT created
these filesystems. The image filesystem's usable capacity is slightly less than
8 GiB because ext4 metadata is inside that limit. This is a disk limit, not a RAM
reservation. Images are created on the NVMe, not in the live USB's 4.7 GiB free
workspace. Existing completed labs are preserved by repeat provisioning.

  Bash Lab     Bash games, scripts and terminal utilities
  Web Lab      Node/npm and Python development tools
  Build Lab    C/C++ build tools, Git, CMake and pkg-config
  Clean Lab    A small Debian environment for testing

The target currently lacks the bootstrap and container executables. Its offline
apt simulation needs only debootstrap, distro-info and systemd-container, with
no upgrades/removals/kernels/firmware. --install-tools authorizes those necessary
host userspace tools; the controller checks the actual package plan again before
installation. Guest development packages are installed inside each image. No
kernel packages or driver modules are restored. Existing loop/ext4 support is
used; if inactive, only those already-installed modules may be loaded, with
blacklists respected. Direct nspawn launches share the dongle's host network without bridges or
veth. An offline/private-network launch is also available. These containers share
the host kernel; they are not virtual machines with separate networking kernels.

  cube-lab plan
  cube-lab status
  sudo cube-lab enter bash
  sudo cube-lab enter web
  sudo cube-lab enter build
  sudo cube-lab enter clean
  sudo cube-lab resources web --cpu 2 --memory-mib 2048

The same four launchers appear in Whitecube's Games & scripts drawer and native
Scripts picker. They use the actual terminal for sudo authentication; the web
service itself still runs as your ordinary user. Exit a lab's shell to stop it.
Guest root is confined to a separate user namespace. Host projects are not
automatically mounted into containers; project manifests can bind one explicit
project read-only. The Labs drawer can save/restore snapshots and set networking.

  sudo cube-lab snapshot bash clean-start
  cube-lab snapshots bash
  sudo cube-lab restore bash clean-start
  sudo cube-lab network-mode web offline
  sudo cube-lab network-mode web shared

Snapshots require a stopped lab and consume another8GiB each. Restore checks
the complete image checksum and retains the current state as a recovery snapshot;
it needs at least16GiB plus512MiB free temporarily. The original remains intact
if validation/copying fails. Partial copies are retained for inspection; see the
container guide before cleanup. A shared/offline selection takes effect on next
launch and never adds veth/bridge modules. Offline means an isolated network
namespace, not a firewall rule over the host connection.

See containers/README.txt and cube-lab
--help for runtime details, provisioned paths, exact guest packages and recovery.

FIRST-BOOT VALIDATION

Whitecube runs cube-check --first-boot once per boot/build and saves the report
under ~/.local/state/whitecube. The Health drawer reruns read-only checks, showing
pending for unprovisioned labs and untested runtime behavior. It does not silently
install tools, configure Wi-Fi or claim that image metadata proves a working lab.

  cube-check
  sudo cube-check --containers

The second command explicitly tests each provisioned image using a bounded,
offline Bash probe, then saves root-owned results. It needs the booted NVMe.
Run it after provisioning; repeat after changing an image. Real compositor/browser
visual review and successful Wi-Fi association must still be checked on hardware.

ROLLBACK

First, if you enabled the networking service, stop it on the booted target:
  sudo systemctl disable --now whitecube-network.service

Restore the specific backup (use / as --root when booted into the NVMe):
  sudo python3 install.py --root /mnt/nvme_root --rollback /mnt/nvme_root/var/backups/whitecube/<timestamp> --apply

Rollback restores replaced files and removes added files. It refuses to erase
files edited after installation. Run systemctl daemon-reload on the booted
target after restoring. Log out/in to switch back to the original compositor.
